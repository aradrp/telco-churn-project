# Telco Customer Churn — Leakage-Safe Prediction & Retention Decision System

A production-quality, portfolio-ready machine learning project that predicts
customer churn for a telecommunications company, explains its decisions, and
recommends a retention action based on **estimated business cost — not
accuracy alone**.

Built against the [Kaggle Telco Customer Churn dataset (BlastChar)](https://www.kaggle.com/datasets/blastchar/telco-customer-churn).

---

## 1. Project Explanation

**Business problem.** A telecom company wants to identify customers likely to
cancel their service so retention teams can intervene — but contacting every
customer is too expensive. This project builds a classifier that estimates
churn probability per customer, translates that probability into an
actionable decision (contact / don't contact) using an explicit business-cost
model, and explains *why* each customer was flagged.

**What makes this "leakage-safe."** All preprocessing that learns anything
from data — imputation medians, one-hot vocabularies, feature scaling,
resampling — lives inside a single `scikit-learn` (or `imbalanced-learn`)
`Pipeline`. That pipeline is fit exclusively on training folds during cross-
validation and only once on the full training set for the final model, so no
statistic derived from validation or test data ever contaminates model
fitting. This is verified directly by a regression test in
`tests/test_pipeline.py`.

**Decision framework, not just a classifier.** Rather than stopping at
"the model is 82% accurate," the project:
1. Compares models on **ROC-AUC / PR-AUC**, not accuracy, because churn is
   an imbalanced class (~20-27% positive rate).
2. Sweeps decision thresholds from 0.05–0.95 and picks the one that
   **minimizes expected business cost**, using an explicit, documented cost
   assumption (`false_negative_cost=$500`, `false_positive_cost=$30`) with a
   sensitivity analysis across alternative cost assumptions.
3. Explains predictions globally (permutation importance / coefficients /
   SHAP) and for individual customers (true/false positive/negative case
   studies), and checks reliability across contract-type subgroups with a
   bootstrap confidence interval on the headline metric.

**A note on the data used in this repo.** No internet access was available
in the environment that built this repository, so `data/raw/telco_churn.csv`
here was generated by a **schema-accurate synthetic data generator**
(`src.data.make_synthetic_telco_data`) rather than downloaded from Kaggle.
Every notebook, script, and saved artifact in this repo ran end-to-end
against that synthetic data as a functional demonstration. **Before treating
any number in `reports/` as a real business finding, replace
`data/raw/telco_churn.csv` with the actual Kaggle CSV and re-run.** The code
itself needs no changes — the real dataset has the identical column schema.

## 3. Installation

```bash
git clone <this-repo-url>
cd telco-churn-project
python3 -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements.txt
```

Get the real dataset:
1. Download `WA_Fn-UseC_-Telco-Customer-Churn.csv` from
   [Kaggle](https://www.kaggle.com/datasets/blastchar/telco-customer-churn).

If you don't have the dataset yet and just want to see the whole project
run, skip step 1–2 and use `--synthetic` below — it generates a
schema-identical demo dataset automatically.

## 4. Running Instructions

### Train the full pipeline end-to-end
```bash
# With the real Kaggle CSV at data/raw/telco_churn.csv
python -m src.train --data data/raw/telco_churn.csv

# OR generate a synthetic demo dataset and train on that (no download needed)
python -m src.train --synthetic --data data/raw/telco_churn.csv
```
This reproduces everything in one command: data audit → clean → split →
model comparison → tuning → imbalance comparison → threshold optimization →
final test evaluation → `predictions.csv` → saved pipeline in `models/`.

### Explore step-by-step in notebooks
```bash
jupyter notebook notebooks/01_data_audit.ipynb
```
Run notebooks in order (01 → 02 → 03 → 04); each writes the artifacts the
next one reads (frozen splits, the fitted pipeline object, etc.).

### Run tests
```bash
pytest tests/ -v
```
Includes a leakage regression test that verifies preprocessing statistics
are learned only from the training fold.

### Score new customers from the command line
```bash
python -m src.predict --input path/to/customers.json
```
where the JSON file is a list of customer records (see `api.py` docstring
for the exact required fields).

### Run the API
```bash
uvicorn api:app --reload --port 8000
```
Then:
```bash
curl -X POST http://localhost:8000/predict \
  -H "Content-Type: application/json" \
  -d '{
    "gender": "Female", "SeniorCitizen": 0, "Partner": "Yes", "Dependents": "No",
    "tenure": 5, "PhoneService": "Yes", "MultipleLines": "No",
    "InternetService": "Fiber optic", "OnlineSecurity": "No", "OnlineBackup": "No",
    "DeviceProtection": "No", "TechSupport": "No", "StreamingTV": "No",
    "StreamingMovies": "No", "Contract": "Month-to-month", "PaperlessBilling": "Yes",
    "PaymentMethod": "Electronic check", "MonthlyCharges": 85.5, "TotalCharges": 427.5
  }'
```
Response:

## 6. Limitations

- **Cost assumptions are illustrative.** `$500` (missed churner) and `$30`
  (unnecessary contact) are stated defaults, not the business's real
  numbers. Replace them (`src/evaluate.py::DEFAULT_FN_COST` /
  `DEFAULT_FP_COST`, or pass `fn_cost=...` to the relevant functions) before
  using the threshold in production.
- **Associations are not causal.** EDA findings (e.g. "month-to-month
  contracts churn more") describe correlation in observational data. Acting
  on them (e.g. pushing customers onto longer contracts) assumes a causal
  relationship that has not been tested here.
- **No temporal/drift validation on real traffic.** The train/val/test split
  is a random stratified split, not a time-based split — it does not
  validate the model's stability as customer behavior or offerings change
  over time. `reports/` includes a placeholder for drift-simulation results
  (Advanced Challenge F) but a production deployment should add real-time
  monitoring.
- **Synthetic data caveat**, restated: any numbers currently in `reports/`
  and `predictions.csv` reflect the synthetic demo dataset used to prove the
  pipeline runs end-to-end in this environment, not real Telco customers.
- **Fairness metrics are calculated but not fully audited.** Subgroup
  reliability (`src/evaluate.py::subgroup_metrics`) is implemented for
  contract type as an example; a full fairness audit across all
  demographic groups (gender, senior citizen status) with minimum
  sample-size thresholds should be completed before any customer-facing
  deployment.

## 7. Advanced Challenges Implemented

| Challenge | Where |
|---|---|
| A. Nested cross-validation | `RandomizedSearchCV` with `StratifiedKFold` in `src/train.py`; outer test-set evaluation is fully held out |
| B. Cost-sensitive learning | `class_weight="balanced"` comparison in `compare_imbalance_strategies` |
| E. Fairness / subgroup reliability | `src/evaluate.py::subgroup_metrics` |
| G. Adversarial data-quality stress test | `OneHotEncoder(handle_unknown="ignore")` + covered by `tests/test_pipeline.py::test_pipeline_handles_unseen_category_gracefully` |
| I. Custom transformer | `src/features.py::DomainFeatureEngineer` (avg charge/tenure-month, service count, tenure buckets) |
| K. Lightweight deployment | `api.py` (FastAPI) |
| L. Reproducibility test | `tests/` + fixed `RANDOM_SEED=42` throughout |

Additional challenges (C: segment-specific thresholds, D: probability
uncertainty via bootstrap, F: drift simulation, H: stacking, J:
explainability stability) have supporting utilities already in
`src/evaluate.py` (e.g. `bootstrap_metric_ci`) and can be extended following
the same patterns.

## 8. Reproducibility

- Global random seed: `RANDOM_SEED = 42` (in `src/data.py`, used throughout).
- All pipeline steps (imputation, scaling, encoding, resampling) are
  scikit-learn / imbalanced-learn `Pipeline` steps, fit only via `.fit()`
  calls on training data — see `tests/test_pipeline.py` for a direct
  regression test proving no cross-fold leakage.
- Exact package versions: see `requirements.txt`.
- To reproduce this exact repository state: `python -m src.train --synthetic --data data/raw/telco_churn.csv`.
